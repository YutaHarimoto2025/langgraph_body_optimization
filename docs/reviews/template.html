A. 報告の作成

  • ファイル名は docs/reviews/standard_<YYYY-MM-DD>.html とする。同名があれば _2、_3 を付ける。
  • 正本は docs/agents/SPEC.md 。実装が正本と食い違う場合は、どちらを直すかを修正案に明記する。
  • 対象は src の実装と、その検証に必要な tests・viewer・params。文献や構想の話は docs/open/ に置き、review の所見にしない。
  • 番号はクリティカル C、修正推奨 R で別々に通しで振る。層が変わっても 1 に戻さない。
  • 層は 5 種類: src / tests / viewer / docs / other。params・resources・スクリプト類は other。修正の中心がある層を 1 つだけ選ぶ。
  • 並び順は src → tests → viewer → docs → other。同層内は重大度、次に修正コストの順。
  • 表の行順は「箇所 / 問題点 / 正本 / 修正案 / 影響範囲 / 言及箇所」で固定。該当のない行は削除し、空欄を残さない。
  • 「箇所」は <path>:L<行>: <記号名> — <コード断片> の形にする。行番号は編集で動くので、記号名とコード断片を同一性の根拠にする。
  • 所見 status は「自動修正可」と「利用者判断が必要」の 2 種類。重大度は C / R の区分で表し、status に持たせない。
  • viewer の見た目の問題はスクリーンショットを <figure class="shot"> に data URI で埋め込む。1 issue あたり 2 枚まで。文章だけで再現できる所見には画像を付けない。
  • 地の文は、結論になる一文だけを <strong> で強調する。表のセルと見出しでは強調しない。
  • チェックボックスの状態は ../open/assets/html-state.js が localStorage に保存する。リセットはページの再読み込みで行う。

B. 修正と検証

  • 「自動修正可」の issue は事前許可を待たずに修正してよい。修正後は pyright・pytest・必要な短い GA run を実行し、「修正完了」と「動作確認完了」を付ける。実行したコマンドは「修正完了」欄に書く。
  • 「利用者判断が必要」の issue は修正しない。判断すべき論点と選択肢を「修正案」に書き、利用者に確認する。
  • 長い GA は回さない。first goal の段階では数分で終わる run までを検証範囲とする。

C. 完了と後片付け

  • 「動作確認完了」が付いた issue は、対応済みとして扱う。未完了の R は checkbox を付けずに残し、次回の報告へ引き継ぐ。
  • 対応が完了した review は docs/reviews/archive/ へ移動する。未完了の R を含む review は移動しない。
  • 移動したら、ファイル内の script のパスを ../../open/assets/html-state.js に直す。移動前の相対パスでは 404 になる。
  • docs/agents/SPEC.md と食い違ったまま残した論点は、7 章の残作業にパス付きで書く。
